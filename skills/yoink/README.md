# yoink

> A skill that yoinks code smells from code some nerd wrote.

`yoink`는 기존 코드베이스를 분석해서 그 프로젝트에서 반복적으로 사용되는 코딩 컨벤션, 설계 방식, 습관, 코드 스멜 등을 추출하는 스킬입니다.

## 왜 만들었나요?

C++을 공부하면서 개인적으로 가장 도움이 많이 됐던 자료 중 하나가 **Google C++ Style Guide**였습니다.

처음에는 왜 이런 규칙을 쓰는지 이해하기 어려운 부분도 많았습니다. 하지만 완전히 이해하지 못하더라도 실제로 코드를 작성할 때 참고할 수 있는 명확한 기준이 있다는 것 자체가 굉장히 도움이 됐습니다. 계속 코드를 작성하고 공부하다 보니 예전에는 이해하지 못했던 규칙들이 왜 존재하는지도 조금씩 알게 됐습니다.

그러다 보니 다른 프로젝트에서도 이런 기준을 가져올 수 있으면 좋겠다고 생각했습니다.

특히 게임 엔진처럼 오래 개발된 C++ 프로젝트를 보면 프로젝트마다 굉장히 강한 개성이 있습니다. 클래스나 변수 이름을 짓는 방법부터 메모리를 관리하는 방식, 객체의 생명주기를 관리하는 방법, 초기화 방식, 자체 자료구조를 사용하는 방식까지 전부 조금씩 다릅니다.

이런 것들은 단순한 코딩 스타일을 넘어서 그 프로젝트를 만든 사람들이 코드를 어떻게 바라보고 설계했는지를 보여준다고 생각합니다.

`yoink`는 그런 것들을 코드에서 찾아내서 다시 사용할 수 있는 형태로 만드는 것을 목적으로 합니다.

## 어디에 쓰나요?

우선은 **공부용**입니다.

잘 만들어진 프로젝트의 코드를 읽으면서 단순히 구현만 보는 것이 아니라, 그 프로젝트에서 반복적으로 사용하는 방식과 규칙을 뽑아낼 수 있도록 만들고 싶었습니다.

새 프로젝트를 시작할 때 참고할 컨벤션을 만드는 용도로도 사용할 수 있습니다. 특정 엔진이나 라이브러리의 스타일이 마음에 든다면 그 코드베이스에서 사용되는 패턴을 분석하고, 이를 자신의 프로젝트에서 참고할 수 있는 규칙으로 만들 수 있습니다.

그리고 AI에게 코드를 작성시키기 위한 스킬이나 지침을 만드는 것도 중요한 목적 중 하나입니다.

## AI가 만드는 맥락 없는 코드

AI가 작성한 코드에서 개인적으로 가장 싫어하는 부분 중 하나는 **코드 자체는 맞는데 프로젝트의 맥락이 없는 경우가 많다는 것**입니다.

컴파일도 되고 기능도 동작하지만, 기존 프로젝트와 전혀 다른 이름을 사용하거나 갑자기 다른 메모리 관리 방식을 사용하고, 기존에 사용하지 않던 추상화나 라이브러리를 가져오는 경우가 있습니다.

파일마다 서로 다른 사람이 작성한 것처럼 보이기도 합니다.

AI가 매번 그럴듯한 코딩 방식을 새로 만들어내도록 하기보다는, 이미 존재하는 코드에서 프로젝트의 규칙을 찾아내고 그 규칙 안에서 코드를 작성하도록 만들고 싶었습니다.

`yoink`는 그런 AI용 코딩 스킬을 만드는 작업을 자동화하기 위해 만들었습니다.

기존 코드에서 반복적으로 나타나는 패턴을 찾아내고 이를 명시적인 규칙으로 만들어두면, AI도 프로젝트의 문맥을 유지하면서 코드를 작성할 수 있습니다.

결과적으로 조금 더 **안정적이고, 일관되고, 재사용 가능하며, 유지보수하기 쉬운 코드**를 작성하도록 유도하는 것이 목표입니다.

## 주의할 점

`yoink`의 가장 큰 문제점은 **좋은 습관만 쌔벼오는 것이 아니라는 점**입니다.

오래된 코드베이스를 분석하다 보면 당시의 언어 제약, 컴파일러 한계, 플랫폼 문제, 성능상의 타협, 이미 사라진 라이브러리의 제약 때문에 생긴 패턴들이 그대로 남아 있는 경우가 많습니다.

그리고 그중에는 말 그대로 나쁜 의미에서의 **코드 스멜**도 포함됩니다.

예를 들어 어떤 패턴이 수천 번 반복된다고 해서 그것이 지금도 반드시 좋은 설계라는 의미는 아닙니다. 단순히 프로젝트가 오래됐기 때문일 수도 있고, 당시에는 다른 선택지가 없었기 때문일 수도 있으며, 이미 프로젝트 내부에서도 제거하고 싶어 하는 레거시일 수도 있습니다.

따라서 `yoink`가 만들어낸 규칙을 그대로 받아들이기보다는 각 규칙의 **Pros / Cons와 절충점(Trade-offs)** 을 충분히 읽어보는 것을 권장합니다.

특히 다음 내용을 이해한 뒤 사용하는 것이 좋습니다.

- 이 규칙은 왜 생겼는가?
- 어떤 문제를 해결하기 위한 것이었는가?
- 당시의 기술적 제약은 무엇이었는가?
- 지금도 같은 제약이 존재하는가?
- 이 규칙을 적용했을 때 얻는 장점은 무엇인가?
- 반대로 어떤 비용이나 위험이 생기는가?
- 프로젝트 전체의 규칙인가, 특정 서브시스템에서만 사용하는 규칙인가?

`yoink`가 생성하는 스킬은 최종 결과물이 아니라 **출발점**에 가깝습니다.

분석된 규칙의 맥락을 직접 이해하고, 필요 없는 규칙은 제거하고, 현재 프로젝트에 맞게 수정하면서 자신만의 스킬로 발전시키는 것을 권장합니다.

모든 코드 스멜이 좋은 코드는 아닙니다.

하지만 가끔은 그 코드 스멜 자체가 그 프로젝트의 스타일이기도 합니다.

그것까지 일단 쌔벼온 뒤, 쓸지는 직접 결정하면 됩니다.
